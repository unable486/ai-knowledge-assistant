# SQL（MySQL 8.0 / InnoDB） > 索引原理与设计

来源：https://fqx.lx.ci/sql-map/

索引是 SQL 性能的全部重点。这块不要背失效清单，要理解 B+ 树的形状：叶子按顺序串成链表、非叶子只放路由键。所有「索引失效」都是同一个原因——你的条件没法在这个有序结构上二分。理解形状之后清单自己就推出来了。

# SQL（MySQL 8.0 / InnoDB） > 索引原理与设计 > B+ 树：为什么是它

来源：https://fqx.lx.ci/sql-map/

索引要解决的是「在磁盘上快速定位」。磁盘 IO 比内存慢几个数量级，所以目标是**把 IO 次数压到最少**。

对比几种结构：

| 结构 | 问题 |
|---|---|
| 二叉搜索树 | 树太高，一百万行约 20 层 = 20 次 IO |
| 哈希表 | O(1) 单点查询，但**不支持范围查询和排序**，`> < BETWEEN ORDER BY` 全废 |
| B 树 | 非叶子也存数据，一个节点能放的路由键变少，树变高 |
| **B+ 树** | 非叶子只放键、叶子放数据且串成有序链表 |

B+ 树的关键设计是**非叶子节点不存数据**：一个 16KB 的页能塞进上千个路由键，于是三层就能索引几千万行——**查任何一行都是 3 次 IO 左右**，而根节点常驻内存，实际 IO 更少。

第二个关键是**叶子节点用双向链表串起来**，且按键有序。这直接给出两个能力：范围查询（定位到起点后顺着链表扫）和排序（索引顺序就是排好的，`ORDER BY` 可以不排序）。

**这两条形状特征是后面所有内容的根**：
- 有序 → 只能从左往右用（最左前缀）
- 有序 → 对列做函数运算后顺序就乱了（函数导致失效）
- 叶子成链 → 范围扫描便宜，随机单点跳跃贵（回表成本）

# SQL（MySQL 8.0 / InnoDB） > 索引原理与设计 > 聚簇索引与二级索引

来源：https://fqx.lx.ci/sql-map/

InnoDB 里数据本身就存在主键的 B+ 树叶子上，这棵树叫**聚簇索引**。一张表只能有一个聚簇索引，因为数据只能按一种顺序物理排列。

**二级索引**（普通索引）的叶子存的是索引列 + **主键值**，不是完整行。所以用二级索引查非索引列，要先拿到主键再去聚簇索引里找整行——这就是**回表**。

```
二级索引 idx_name          聚簇索引（主键）
叶子: ('张三', id=42)  →   叶子: id=42 → 整行数据
```

这个结构解释了两件事：

**一、主键必须短。** 每个二级索引的每个叶子条目都带一份主键值。主键用 `BIGINT`（8 字节）还是 `CHAR(36)` 的 UUID（36 字节），在 5 个二级索引、1000 万行的表上差出几个 GB。

**二、主键必须递增。** 聚簇索引按主键顺序存放，自增主键是**顺序追加**，页填满了开新页；UUID 是随机值，新行要插到中间，会触发**页分裂**——把一个满页拆成两个半满页。后果是磁盘空间浪费近一半、写入变慢、缓存命中率下降。

现象：用 UUID 主键的表，插入速度随数据量增长明显下降，`SHOW TABLE STATUS` 里 `Data_free` 很大，同样行数的表体积比自增主键的大一截。

**要有序又要全局唯一**，两条路：数据库层用自增（分库时配步长或用号段），应用层用**有序 UUID**（时间戳在高位，如 UUIDv7 / ULID）。MySQL 8 也可以用 `UUID_TO_BIN(uuid, 1)` 把时间位换到前面再存 `BINARY(16)`。

**没显式定主键会怎样**：InnoDB 会挑一个非空唯一索引，没有就自己生成一个 6 字节的隐藏 `row_id`。这个 row_id 是**全库共享的一个计数器**，高并发插入时它是争用点。所以每张表都要显式主键。

# SQL（MySQL 8.0 / InnoDB） > 索引原理与设计 > 聚簇索引与二级索引 > 回表与覆盖索引

来源：https://fqx.lx.ci/sql-map/

**回表就是「二级索引给了主键，还得去聚簇索引取整行」这一次额外查找。** 单次很快，但一次查询返回一万行就是一万次随机 IO，慢查询里这部分经常是主要成本。

**覆盖索引**是消除回表的手段：如果 SELECT 需要的所有列都在这个索引里，就不用回表了。

```sql
-- 索引 (user_id, created_at)
SELECT user_id, created_at FROM orders WHERE user_id = 1;   -- 覆盖，不回表
SELECT * FROM orders WHERE user_id = 1;                     -- 要回表
```

判断方法是 EXPLAIN 的 Extra 列出现 **`Using index`**（注意不是 `Using index condition`，那是索引下推）。

**这是 `SELECT *` 的真实代价之一**：多取的那几列可能让一个本来能覆盖的索引失去覆盖能力，从零回表变成 N 次回表。所以高频查询应该显式列出需要的列，反过来也可以为高频查询专门加一个「宽一点」的联合索引让它覆盖。

代价要说清楚：把列加进索引会让索引变大、写入变慢。**只为真正高频的查询做覆盖优化**，不要给每个查询都配一个覆盖索引。

# SQL（MySQL 8.0 / InnoDB） > 索引原理与设计 > 联合索引与最左前缀

来源：https://fqx.lx.ci/sql-map/

联合索引 `(a, b, c)` 的排序规则是：先按 a 排，a 相同再按 b，b 相同再按 c。像按姓、名、年龄排好的名册。

**最左前缀原则**由这个顺序直接推出：只有从最左边连续用起，才能在有序结构上二分。

```sql
-- 索引 (a, b, c)
WHERE a = 1                    -- ✓ 用到 a
WHERE a = 1 AND b = 2          -- ✓ 用到 a, b
WHERE a = 1 AND b = 2 AND c = 3 -- ✓ 全用上
WHERE b = 2                    -- ✗ 跳过了 a，用不上（可能退化成索引扫描）
WHERE a = 1 AND c = 3          -- △ 只用到 a，c 用不上（b 断了）
```

**条件的书写顺序不重要**，优化器会调整：`WHERE b = 2 AND a = 1` 照样能用。断的是「索引列的连续性」，不是「你写的顺序」。

**范围条件后面的列用不上。** `WHERE a = 1 AND b > 10 AND c = 5`：a 精确、b 范围，到 b 就停了，c 只能在结果里过滤。原因还是顺序——b 一旦是范围，这些行的 c 就不再有序了。

**所以联合索引的列顺序要这样定**：等值条件的列放前面，范围条件的列放最后。一个高频查询是 `WHERE tenant_id = ? AND status = ? AND created_at > ?`，索引就建 `(tenant_id, status, created_at)`。

**`ORDER BY` 也吃最左前缀**：`WHERE a = 1 ORDER BY b` 能用 `(a, b)` 避免排序；`ORDER BY b, c` 的方向必须一致（都升或都降），混着 `b ASC, c DESC` 在 MySQL 8 之前没法用索引（MySQL 8 支持降序索引 `INDEX (b ASC, c DESC)` 可以处理）。

**一个联合索引顶多个单列索引**：有了 `(a, b, c)`，再建 `(a)` 就是浪费。反过来，三个单列索引 `(a)``(b)``(c)` 处理 `WHERE a=1 AND b=2` 时通常只能用一个（索引合并有条件且不总是更快）。**优先建联合索引**。

# SQL（MySQL 8.0 / InnoDB） > 索引原理与设计 > 索引失效的完整清单

来源：https://fqx.lx.ci/sql-map/

每一条都是「条件没法在有序结构上二分」的一个变体。

**一、对列做函数运算或计算。**

```sql
-- ✗ 索引上存的是 created_at 的值，不是 DATE(created_at) 的值
WHERE DATE(created_at) = '2026-09-09'
-- ✓ 改成范围，索引可用
WHERE created_at >= '2026-09-09' AND created_at < '2026-09-10'

-- ✗
WHERE amount / 100 > 50
-- ✓ 把运算移到常量侧
WHERE amount > 5000
```

MySQL 8.0.13+ 支持**函数索引**（`INDEX ((DATE(created_at)))`），确实必须按函数结果查时可以建，但优先改写条件。

**二、隐式类型转换。** 这条最阴，因为语句看起来毫无问题：

```sql
-- phone 是 varchar，传了数字
WHERE phone = 13800138000     -- ✗ 全表扫描
WHERE phone = '13800138000'   -- ✓
```

字符串列和数字比较时，MySQL 把**字符串转成数字**（不是反过来），等于对列做了函数运算，索引失效。反过来 int 列传字符串 `WHERE id = '42'` 是安全的——转的是常量那侧。

现象：某个接口莫名慢，EXPLAIN 显示 `type: ALL`，而同样的语句手动带引号跑就快。**排查慢查询时先看每个条件的类型是否匹配**，这条的命中率很高。字符集不一致（JOIN 两个表的关联列一个 utf8mb4 一个 utf8）也会触发同样的问题。

**三、前导模糊匹配。** `LIKE '%abc'` 和 `LIKE '%abc%'` 用不上索引（不知道从哪个前缀开始找），`LIKE 'abc%'` 可以。要做包含匹配，用全文索引或搜索引擎。

**四、`OR` 连接的列不都有索引。** `WHERE a = 1 OR b = 2`，只有 a 有索引时整体退化成全表扫描。两个列都有索引时可能走索引合并，但不保证。改写成 `UNION` 更可控。

**五、`!=` `<>` `NOT IN` `IS NOT NULL` 选择性差时优化器主动放弃。** 这不是「不能用」，是「用了更慢」——要扫的行占比太高，回表成本超过全表顺序扫描。

**六、联合索引跳列或范围后置**（上一节）。

**七、区分度太低。** 性别、状态这种只有几个值的列，单独建索引通常没用——优化器算出要扫一大半行，直接全表扫。这类列适合放在联合索引里当第二列，或者配合区分度高的列一起用。

# SQL（MySQL 8.0 / InnoDB） > 索引原理与设计 > 索引失效的完整清单 > 索引下推（ICP）

来源：https://fqx.lx.ci/sql-map/

**索引条件下推**（Index Condition Pushdown，MySQL 5.6+）让存储引擎在**索引层面**就把不满足条件的行过滤掉，而不是先回表拿到整行再由 server 层过滤。

场景：索引 `(a, b)`，查询 `WHERE a = 1 AND b LIKE '%x%'`。b 上的模糊匹配用不上索引排序，但 **b 的值就在索引里**。没有 ICP 时，引擎把所有 a=1 的行都回表，再由 server 层挑 b；有 ICP 时，引擎在索引里先判断 b，只回表真正需要的行。

**收益是减少回表次数**，a=1 有一万行、其中只有十行匹配 b 时，回表从一万次降到十次。

EXPLAIN 的 Extra 里显示 **`Using index condition`** 就是用上了。注意和 `Using index`（覆盖索引，完全不回表）区分——前者还是要回表，只是少回。

ICP 是自动的，不用写什么。知道它的意义在于**解释「为什么这个用不上索引的条件放进联合索引里还是变快了」**，以及看懂 EXPLAIN 输出。它对覆盖索引无效（本来就不回表），对主键聚簇索引扫描也不适用。

# SQL（MySQL 8.0 / InnoDB） > 索引原理与设计 > 什么时候不该建索引

来源：https://fqx.lx.ci/sql-map/

索引不是免费的，代价有三块：

**一、写入变慢。** 每次 INSERT / UPDATE / DELETE 都要维护所有相关索引的 B+ 树，可能触发页分裂。一张表挂十个索引，写入吞吐会明显下降。

**二、占空间。** 每个二级索引都是一棵完整的 B+ 树，包含索引列 + 主键。大表上索引总体积超过数据本身很常见。

**三、优化器负担。** 候选索引越多，优化器选错的概率越大（见执行计划那一章）。

**不该建的几种情况**：

- **区分度太低的列**（`is_deleted`、`status` 只有两三个值）。判断标准：`SELECT COUNT(DISTINCT col) / COUNT(*) FROM t`，这个值太小就没意义。区分度低的列适合放进联合索引，不适合单独建
- **很少出现在查询条件里的列** —— 索引是为查询建的，不是为「看起来重要」建的
- **已经被联合索引最左前缀覆盖的单列** —— 有 `(a, b)` 就不要再建 `(a)`
- **频繁更新的列** —— 每次更新都要调整索引
- **小表** —— 几百行的表全表扫描比走索引还快，优化器也会这么选

**长字符串列用前缀索引**：`INDEX (url(64))` 只索引前 64 个字符，省空间。代价是**没法用于覆盖索引和排序**（索引里存的不是完整值）。选多长看区分度：`SELECT COUNT(DISTINCT LEFT(url, 64)) / COUNT(*) FROM t`，接近完整列的区分度就够了。

**怎么知道哪些索引没被用过**：MySQL 8 的 `sys.schema_unused_indexes` 视图直接列出来。删之前要确认统计周期够长（月末报表可能只在月末用），且要考虑主从——从库上的查询用的索引在主库看不出来。

# SQL（MySQL 8.0 / InnoDB） > 索引原理与设计 > 怎么为一个查询设计索引

来源：https://fqx.lx.ci/sql-map/

固定流程，比凭感觉建靠谱：

**一、把查询的 WHERE / ORDER BY / SELECT 列出来。** 例：

```sql
SELECT id, title, created_at FROM doc
WHERE tenant_id = ? AND status = 1 AND created_at > ?
ORDER BY created_at DESC LIMIT 20;
```

**二、等值条件的列放前面，按区分度从高到低。** `tenant_id` 区分度高、`status` 低，所以 `(tenant_id, status, ...)`。

**三、范围条件和排序列放最后。** `created_at` 既是范围又是排序，放第三位：`(tenant_id, status, created_at)`。这样 `ORDER BY created_at DESC` 能直接利用索引顺序，避免 filesort。

**四、看能不能顺手做成覆盖索引。** SELECT 要 `id, title, created_at`——id 是主键（二级索引叶子里本来就有），`created_at` 已在索引里，只缺 `title`。如果这个查询非常高频，可以建 `(tenant_id, status, created_at, title)` 换取零回表；如果 title 很长，不值得。

**五、用 EXPLAIN 验证，而不是相信推理。** 看 `key` 是不是用了预期的索引、`rows` 是不是接近实际返回行数、Extra 里有没有 `Using filesort` / `Using temporary`。

**六、检查是否和已有索引重复。** 已有 `(tenant_id, status)` 时，新建 `(tenant_id, status, created_at)` 之后前者就可以删了——**它是新索引的最左前缀**。

最后一条经验：**先让查询走对索引，再考虑覆盖**。前者通常是几十倍的差距，后者是百分之几十。
