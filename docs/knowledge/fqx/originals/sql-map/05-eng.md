# SQL（MySQL 8.0 / InnoDB） > 工程实践 > 字段类型怎么选

来源：https://fqx.lx.ci/sql-map/

**金额绝对不能用 `FLOAT` / `DOUBLE`。** 二进制浮点数表示不了精确小数，`0.1 + 0.2 != 0.3`。现象是对账差几分钱、同一笔金额存进去读出来不一样。两条正确路线：

- `DECIMAL(18, 2)` —— 精确十进制，数据库层面支持运算
- `BIGINT` 存**最小单位（分）** —— 更快、不可能忘记设精度，电商和收银系统常用

**时间类型**：

| 类型 | 范围 | 时区 |
|---|---|---|
| `DATETIME` | 1000~9999 年，8 字节（8.0 是 5 字节+小数位） | **不转换**，存什么读什么 |
| `TIMESTAMP` | 1970~2038 年，4 字节 | 存 UTC，读按会话时区转换 |
| `INT` 存 Unix 秒 | 2038 问题 | 自己管 |

**`TIMESTAMP` 的 2038 年上限是硬伤**，新表不要用它存业务时间。**推荐 `DATETIME` + 应用层统一用 UTC**：时区转换放在应用层做，数据库里存的值永远确定，跨时区部署和数据迁移都不会变样。用 `TIMESTAMP` 的自动时区转换在多时区场景下会造成「同一行数据不同人看到不同时间」。

**`VARCHAR(n)` 里的 n 是字符数不是字节数**（MySQL 4.1+）。`VARCHAR(255)` 这个习惯来自早期版本的索引限制，现在没有特殊意义。n 的实际影响有两处：一是**内部临时表和排序时按最大长度分配内存**，所以 `VARCHAR(4000)` 存短字符串会让排序变贵；二是索引前缀长度受限。**按业务真实上限给**，手机号 20、邮箱 128、标题 255，不要一律 255 也不要一律 65535。

**字符集用 `utf8mb4`，不要用 `utf8`。** MySQL 的 `utf8` 是残缺实现（最多 3 字节），存不了 emoji 和部分生僻字，插入时报 `Incorrect string value`。MySQL 8 默认已是 utf8mb4。**JOIN 两张表的关联列字符集不一致会导致隐式转换、索引失效**，建库时统一定好。

**`ENUM` 少用**：加一个值要 DDL，且不同版本行为有差异。用 `TINYINT` + 应用层常量，或者单独一张字典表。

**`TEXT` / `BLOB` 单独放一张表**：InnoDB 里大字段可能溢出到额外页，`SELECT *` 会把它们全读出来。把正文类字段拆到附属表，主表保持窄，扫描和缓存效率都更好。

# SQL（MySQL 8.0 / InnoDB） > 工程实践 > 主键、唯一约束与软删除

来源：https://fqx.lx.ci/sql-map/

**每张表都要显式主键**，用自增 `BIGINT` 或有序 UUID（理由见索引章：聚簇索引 + 页分裂）。没主键时 InnoDB 用一个全库共享的隐藏计数器，高并发插入时是争用点。

**唯一约束要建在数据库层**，不能只靠应用层查一下再插：

```sql
-- ✗ 并发下两个请求都查到「不存在」，都插入成功
SELECT id FROM users WHERE email = ?;   -- 没有
INSERT INTO users (email) VALUES (?);

-- ✓ 数据库唯一索引兜底，第二个插入直接冲突
ALTER TABLE users ADD UNIQUE KEY uk_email (email);
```

**唯一索引是幂等性最可靠的实现**：重复请求带同一个幂等键，第二次插入报 `Duplicate entry`，捕获这个错误返回「已处理」即可。比 Redis 记键、比先查后插都可靠，因为它是数据库层的原子保证。

**软删除（`is_deleted` / `deleted_at`）的三个坑**：

**一、唯一约束失效。** `UNIQUE (email)` 加上软删除后，删了再注册同一个邮箱会冲突。修法是把删除标记加进唯一索引：`UNIQUE (email, deleted_at)`，且未删除时 `deleted_at` 用固定值（不能用 NULL——多个 NULL 不冲突，但也就失去了约束）。或者用 `UNIQUE (email, is_deleted)` 配合「删除时把 email 改名」。

**二、每个查询都要记得加条件。** 漏一处就查出已删数据。用视图或 ORM 的全局过滤器统一处理，不要靠人记。

**三、数据只增不减。** 软删除的行永远占空间和索引。高频删除的表要配归档策略，定期把 `is_deleted=1` 且超过保留期的行搬到归档表。

判断依据：**真的需要恢复能力或审计追溯才用软删除**。日志类、明细类数据直接物理删除 + 归档更简单。

# SQL（MySQL 8.0 / InnoDB） > 工程实践 > SQL 注入与参数化

来源：https://fqx.lx.ci/sql-map/

**注入的根源是把用户输入拼进了 SQL 文本**，于是输入里的引号和关键字改变了语句结构。

```
输入: ' OR '1'='1
拼出: SELECT * FROM users WHERE name = '' OR '1'='1'   -- 返回全表
```

**预编译（参数化）为什么能防**：`?` 占位符走的是**协议层的参数绑定**，SQL 模板先发给服务器解析成执行计划，参数单独传。参数永远被当成一个**值**，不参与语法解析。所以 `' OR '1'='1` 就是一个普通字符串，去匹配 name 字段。

附带收益是**执行计划可复用**，同一模板不同参数不用重复解析。

```js
// ✗ 字符串拼接 —— 注入
db.query(`SELECT * FROM users WHERE name = '${name}'`);

// ✓ 参数化
db.query('SELECT * FROM users WHERE name = ?', [name]);
```

**必须知道的一条：占位符不能用在标识符位置。** 表名、列名、`ORDER BY` 的字段、`ASC/DESC` 都不是值，只能拼接。这些位置**唯一的正确做法是白名单**，不是转义：

```js
// ✓ 白名单，不在名单里就用默认值
const SORTABLE = new Set(['created_at', 'updated_at', 'amount']);
const sortField = SORTABLE.has(req.query.sort) ? req.query.sort : 'created_at';
const sortDir = req.query.dir === 'desc' ? 'desc' : 'asc';
const sql = `SELECT * FROM orders ORDER BY ${sortField} ${sortDir} LIMIT ?`;
```

**为什么必须白名单而不是转义**：`ORDER BY` 位置可以塞子查询，攻击者能用它做布尔盲注——每次请求根据排序结果不同推断出一位信息，慢慢把整表读出来。而你的日志里看到的只是一堆「正常的」查询，没有任何报错。

**`LIKE` 的拼接**也是常见注入口：

```sql
-- ✗
LIKE '%${keyword}%'
-- ✓ 拼接交给数据库函数
LIKE CONCAT('%', ?, '%')
```

**其他防线**：数据库账号按最小权限给（应用账号不需要 DROP、不需要 FILE 权限）；错误信息不要直接返回给前端（暴露表结构）；ORM 不是免疫的——ORM 提供的 `raw` / `whereRaw` 接口一样能注入。

**怎么保证不出漏网的**：靠评审看不住，要让 CI 拦。扫描代码里的字符串拼接 SQL（模板字符串里出现 SELECT/INSERT/WHERE 且带插值），把排序参数集中到一个校验函数里，然后**在测试环境用带引号、注释符、`UNION SELECT` 的畸形参数实测一遍**——这一步是唯一能证明防线真的生效的动作。

# SQL（MySQL 8.0 / InnoDB） > 工程实践 > 连接池

来源：https://fqx.lx.ci/sql-map/

建立数据库连接要 TCP 握手 + 认证，几毫秒到几十毫秒。每个请求都新建连接，这部分开销会超过查询本身。连接池预先建好连接复用。

**连接数不是越大越好。** 数据库端每个连接都要内存（排序缓冲、连接缓冲）和一个线程/进程。连接数超过 CPU 能有效调度的量之后，**增加连接只会增加上下文切换和锁竞争，吞吐反而下降**。

现象：把池子从 20 调到 200 之后，平均响应时间变长、数据库 CPU 打满但 QPS 没涨。

经验起点是 **CPU 核数的 2~4 倍**，然后压测调整。真正的约束是数据库的 `max_connections` 和它能承受的并发。注意**多实例部署要乘以实例数**：10 个实例每个池 20，数据库端就是 200 个连接。

**几个关键参数**（以 HikariCP 命名为例，其他池类似）：

| 参数 | 作用 | 常见坑 |
|---|---|---|
| `maximum-pool-size` | 池上限 | 乘以实例数别超过 `max_connections` |
| `connection-timeout` | 拿不到连接等多久失败 | 太长会让请求堆积，建议几秒 |
| `max-lifetime` | 连接最长存活时间 | **必须小于数据库的 `wait_timeout`** |
| `idle-timeout` | 空闲回收 | 小于 max-lifetime |

**`max-lifetime` 比数据库 `wait_timeout` 长会出偶发错误**：数据库端已经把空闲连接关了，池子不知道，拿出来用时报 `Connection is closed` 或 `Communications link failure`。现象是低峰期偶发失败、高峰期反而正常（连接一直在用不会空闲超时）。**排查偶发连接错误先对比这两个值**。

**连接泄漏**：拿了连接不还（没关、异常路径漏了关）。现象是运行一段时间后所有请求卡在获取连接上，然后集体超时。HikariCP 的 `leak-detection-threshold` 能在连接被持有超过阈值时打警告栈，定位到是哪段代码没还。

**事务和连接的关系要清楚**：一个事务绑定一个连接。事务里做耗时的外部调用，那个连接就一直被占着——这是长事务把连接池打满的机制（见事务章）。

# SQL（MySQL 8.0 / InnoDB） > 工程实践 > 读写分离与主从延迟

来源：https://fqx.lx.ci/sql-map/

主库写、从库读，是最常用的扩展方式。代价是**从库有延迟**，于是出现「刚写完读不到」。

**延迟的来源**：主库写 binlog → 传给从库 → 从库回放。回放是相对串行的（MySQL 5.7+ 有并行回放但受限于事务分组），主库高并发写入时从库跟不上。

**现象很具体**：用户提交表单后跳转到详情页，详情页显示「不存在」或还是旧数据；刷新一下就好了。这类 bug 在开发环境（单库）永远复现不出来。

**怎么看延迟**：

```sql
SHOW REPLICA STATUS;    -- MySQL 8.0.22+；老版本是 SHOW SLAVE STATUS
-- 看 Seconds_Behind_Source（老版本 Seconds_Behind_Master）
```

这个值不完全可靠（它算的是「正在回放的事务在主库上的执行时间和现在的差」，主库空闲时会显示 0 即使实际有积压）。更准的是用心跳表：主库定时写一个时间戳，从库读出来和当前时间比。

**应对策略，按可靠性**：

1. **写后读走主库** —— 最简单可靠。写操作之后的一小段时间内（或同一个请求内）强制读主库。多数框架支持按注解或按线程上下文标记
2. **业务上避免立即读** —— 提交后直接用请求返回的数据渲染，不要再查一次
3. **等待同步位点** —— 写完拿到 binlog 位点，读之前确认从库已回放到该位点（`WAIT_FOR_EXECUTED_GTID_SET`）。准确但增加延迟
4. **关键路径全部走主库** —— 账务、库存这类不能容忍旧数据的，直接不做读写分离

**别用「延迟一般只有几十毫秒」当设计前提**：大事务、DDL、批量导入都会让延迟瞬间飙到几十秒。设计时假设延迟可能很大，才不会在促销日出事。

# SQL（MySQL 8.0 / InnoDB） > 工程实践 > 大表 DDL 的在线方案

来源：https://fqx.lx.ci/sql-map/

**给大表加字段/加索引，原始做法会锁表**——期间所有写入阻塞，几百万行的表可能锁几分钟到几十分钟，等于服务停摆。

**MySQL 8 的原生能力先确认**：

- **Instant DDL**（8.0.12+）—— **加列**（末尾）、改列名、加/删默认值这类只改元数据的操作**瞬间完成**，不动数据。语法 `ALTER TABLE t ADD COLUMN c INT, ALGORITHM=INSTANT`。**指定 ALGORITHM=INSTANT 的好处是不支持时直接报错**，而不是悄悄退化成慢方案
- **Online DDL**（`ALGORITHM=INPLACE`）—— 加索引等操作允许并发读写，但**开始和结束仍需要短暂的元数据锁**
- 改列类型、改字符集、加主键这类通常仍需 `COPY`，要走外部工具

**元数据锁（MDL）是最容易踩的坑**：即使是 Online DDL，获取 MDL 时如果有**长事务正在访问这张表**，DDL 就会等；而 DDL 在等的期间，**后续所有对这张表的查询都会排在它后面等**。现象是一条「在线」的 DDL 把整张表的读写全堵住了，看起来像 DDL 锁表，实际是长事务 + MDL 队列。

**所以大表 DDL 之前必须**：查 `information_schema.innodb_trx` 确认没有长事务，给 DDL 设 `lock_wait_timeout` 避免无限等待，选低峰期执行。

**外部工具**（改列类型、超大表加索引时用）：

| 工具 | 原理 |
|---|---|
`pt-online-schema-change` | 建影子表 → 触发器同步增量 → 分批拷数据 → 原子改名 |
`gh-ost` | 建影子表 → **读 binlog** 同步增量 → 分批拷数据 → 改名 |

**gh-ost 更推荐**：不用触发器（触发器会拖慢原表的每次写入），且支持暂停、限速、动态调参。两者都需要表有主键或唯一键。

**通用注意**：都要额外一份表空间（磁盘至少留出表大小的余量）；改名瞬间仍有极短的锁；执行期间主从延迟会上升，要配限速。

**回滚方案要预先想好**：加字段可以直接删（Instant 很快），加索引可以先设 `INVISIBLE` 观察再删。改列类型的回滚是再改回去——同样是一次大 DDL，所以改类型前一定要在同规模的测试数据上演练过。

# SQL（MySQL 8.0 / InnoDB） > 工程实践 > 大表 DDL 的在线方案 > 备份、binlog 与恢复

来源：https://fqx.lx.ci/sql-map/

**备份分两类**：

- **逻辑备份**（`mysqldump` / `mysqlpump`）—— 导出 SQL 语句。跨版本、可读、可选表恢复；缺点是大库很慢，恢复更慢
- **物理备份**（`xtrabackup` / 文件快照）—— 直接拷数据文件。快得多，适合大库；要求版本和目录结构匹配

**`mysqldump` 必须加 `--single-transaction`**（InnoDB），否则会锁表。它靠一个一致性快照导出，不阻塞写入：

```bash
mysqldump --single-transaction --source-data=2 -u user -p db > db.sql
```

`--source-data=2`（老版本 `--master-data=2`）会把 binlog 位点写进备份注释里——**这是做时间点恢复的前提**。

**binlog 的两个作用**：主从复制、时间点恢复（PITR）。有全量备份 + 之后的 binlog，就能恢复到任意时刻。这是「误删数据」的唯一救命手段：

```bash
# 1. 恢复全量备份
# 2. 用 binlog 重放到误操作发生前的那一刻
mysqlbinlog --stop-datetime='2026-09-09 14:29:59' mysql-bin.000123 | mysql -u user -p
```

**`binlog_format` 用 `ROW`**（记录行的前后值）而不是 `STATEMENT`（记录 SQL）。ROW 格式在主从一致性上可靠得多，且**误删数据后能从 binlog 里反解出被删的行**（用 `mysqlbinlog -v --base64-output=DECODE-ROWS` 或 binlog2sql 之类工具生成反向 SQL）。代价是 binlog 体积大。

**最重要的一条：定期演练恢复。** 没验证过的备份等于没有备份——权限不对、文件损坏、版本不兼容、缺 binlog 位点，这些问题只有真恢复一次才会暴露。演练要记录**实际恢复耗时**，这个数字才是你真正的 RTO。

# SQL（MySQL 8.0 / InnoDB） > 工程实践 > 分库分表：最后手段

来源：https://fqx.lx.ci/sql-map/

**先确认真的到瓶颈了。** 单表几千万行、配好索引、SQL 写对的情况下，MySQL 通常还能正常工作。分表之前该先做的：

1. 优化慢查询（前面几章）
2. 归档历史数据 —— 订单表只留近一年，历史进归档表。**这一步能解决大部分「表太大」的问题，成本远低于分表**
3. 加从库分担读
4. 冷热字段拆表（大字段挪走）
5. 引入缓存

**分区表**（`PARTITION BY RANGE`）是中间选项：逻辑一张表、物理多个文件，按时间分区时删历史数据只需 `DROP PARTITION`（瞬间完成，不产生大量 undo）。限制是分区键必须包含在所有唯一索引里，跨分区查询仍要扫多个分区。

**真要分片，先定分片键**。这是整个方案里最难改的决定：

- 必须是**绝大多数查询都会带的字段**——不带分片键的查询要广播到所有分片再合并，性能和复杂度都差
- 要考虑数据分布均匀（按用户 id 哈希通常比按地区均匀）
- 电商常见按买家 id 分片，那么「查某商家的所有订单」就要走另一套（冗余一份按卖家分片的数据，或走搜索引擎）

**分片后失去的能力**，每一条都要有替代方案：

| 失去 | 替代 |
|---|---|
| 跨分片 JOIN | 冗余字段、或应用层多次查询后拼装 |
| 跨分片事务 | 最终一致（本地消息表 / 事务消息）、或 XA（性能差） |
| 全局自增主键 | 雪花 id、号段模式、有序 UUID |
| 跨分片分页排序 | 各分片取前 N 再归并（深分页时代价大） |
| 全局唯一约束 | 单独一张全局唯一表，或分片键内唯一 |

**扩容也要预先设计**：按 mod 分片时扩容要搬几乎全部数据。用**一致性哈希**或**预分片**（先分成 1024 个逻辑片，映射到 4 个物理库，扩容时只搬映射）能大幅降低搬迁量。

**一句判断**：分库分表带来的复杂度是长期的、影响每一次开发的；而它解决的问题往往还有更便宜的解法。**归档 + 索引优化没做尽之前，不要碰分片。**
