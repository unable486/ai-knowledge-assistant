# SQL（MySQL 8.0 / InnoDB） > 事务与并发控制

来源：https://fqx.lx.ci/sql-map/

事务这块容易背成一堆名词。抓两条线：ACID 的每个字母各自靠一个具体机制实现（undo log / redo log / 锁 + MVCC）；隔离级别的四档是「允许哪些读异常」的四种取舍。理解这两条，锁和 MVCC 就是工具而不是知识点。

# SQL（MySQL 8.0 / InnoDB） > 事务与并发控制 > ACID 各自靠什么实现

来源：https://fqx.lx.ci/sql-map/

四个特性不是抽象口号，每个都对应一个具体机制：

| 特性 | 含义 | 靠什么实现 |
|---|---|---|
| **原子性** A | 全成功或全回滚 | **undo log**（记录反向操作，回滚时执行） |
| **一致性** C | 从一个合法状态到另一个合法状态 | 约束 + 其余三个特性共同保证 |
| **隔离性** I | 并发事务互不干扰 | **锁 + MVCC** |
| **持久性** D | 提交后不丢 | **redo log**（先写日志再改数据页） |

**undo log 是回滚的依据**：insert 记下「删掉这行」，update 记下旧值。回滚时把 undo 反着执行一遍。undo log 同时也是 MVCC 的版本来源——这是它最容易被忽略的第二个作用。

**redo log 解决的是「改了内存还没落盘就宕机」**。InnoDB 改数据先改内存页（buffer pool），脏页异步刷盘。如果只有这个机制，宕机就丢数据。所以提交前先把「这个页的这个位置改成什么」顺序追加到 redo log，落盘后才算提交成功。崩溃恢复时重放 redo log。

**为什么 redo log 比直接刷数据页快**：redo 是顺序追加写，数据页是随机写。顺序写磁盘比随机写快一两个数量级。这套思路叫 WAL（Write-Ahead Logging），几乎所有数据库都用。

**binlog 和 redo log 不是一回事**，容易混：

- **redo log** 是 InnoDB 引擎层的，物理日志（「某页某偏移改成什么」），循环写覆盖，用于崩溃恢复
- **binlog** 是 MySQL server 层的，逻辑日志（「执行了什么语句」或「某行改成什么」），追加不覆盖，用于**主从复制和时间点恢复**

两者要保持一致，靠**两阶段提交**：写 redo（prepare）→ 写 binlog → 提交 redo（commit）。中间任一步崩溃都能恢复出一致状态。

**持久性的实际强度取决于配置**：`innodb_flush_log_at_trx_commit=1` 每次提交都 fsync（最安全，默认）；设成 2 或 0 性能更好但宕机可能丢最后一秒的事务。这个参数是「性能 vs 丢数据」的直接开关，改之前要确认业务能不能接受。

# SQL（MySQL 8.0 / InnoDB） > 事务与并发控制 > 四个隔离级别与三类读异常

来源：https://fqx.lx.ci/sql-map/

三类读异常，按严重程度：

- **脏读** —— 读到别的事务**还没提交**的数据。对方回滚了，你读到的值从来不存在
- **不可重复读** —— 同一事务内两次读**同一行**，值不一样（别人改了并提交）
- **幻读** —— 同一事务内两次执行**同一范围查询**，行数不一样（别人插了新行）

四个隔离级别就是允许哪些异常：

| 级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交 READ UNCOMMITTED | 可能 | 可能 | 可能 |
| 读已提交 READ COMMITTED | 不会 | 可能 | 可能 |
| 可重复读 REPEATABLE READ | 不会 | 不会 | **InnoDB 下基本不会** |
| 串行化 SERIALIZABLE | 不会 | 不会 | 不会 |

**MySQL 默认是可重复读（RR），这和大多数数据库不同**——PostgreSQL、Oracle、SQL Server 默认都是读已提交（RC）。MySQL 选 RR 的历史原因是早期 binlog 只有 statement 格式，RC 下会导致主从数据不一致。

**「RR 解决不了幻读」这个说法要修正。** 标准 SQL 里 RR 允许幻读，但 **InnoDB 的 RR 用间隙锁把幻读基本堵住了**——范围查询时锁住的不只是存在的行，还有行之间的间隙，别人插不进来。

但有一个漏口：**快照读和当前读混用**。

```sql
-- 事务 A
BEGIN;
SELECT * FROM t WHERE id = 5;        -- 快照读，返回空
-- 事务 B 插入 id=5 并提交
SELECT * FROM t WHERE id = 5;        -- 还是空（快照）
UPDATE t SET v = 1 WHERE id = 5;     -- 当前读！影响 1 行
SELECT * FROM t WHERE id = 5;        -- 现在看得到了 —— 幻读
```

这不是 bug，是快照读和当前读两套机制的交界处。实际影响：靠 `SELECT` 判断「不存在所以插入」在并发下不可靠，要用唯一索引兜底。

**很多互联网团队把 MySQL 改成 RC**，理由是：间隙锁范围大、死锁概率高；RC 下锁范围小、并发更好；业务通常自己用版本号或唯一约束保证正确性。改不改是取舍，但**要知道自己跑在哪个级别**：`SELECT @@transaction_isolation`。

# SQL（MySQL 8.0 / InnoDB） > 事务与并发控制 > MVCC：不加锁的读

来源：https://fqx.lx.ci/sql-map/

MVCC（多版本并发控制）让**读不阻塞写、写不阻塞读**。原理是每行数据保留多个版本，每个事务读到「对它可见的那个版本」。

**三个组成部分**：

**一、行上的隐藏列。** 每行除了业务字段还有 `DB_TRX_ID`（最后修改它的事务 id）和 `DB_ROLL_PTR`（指向 undo log 里的上一个版本）。

**二、版本链。** 一行被改三次，undo log 里就串着三个旧版本，通过 roll_ptr 连成链表。

**三、ReadView。** 事务读数据时生成一个「快照」，记录当时哪些事务还活跃。沿版本链往下找，找到第一个「对我可见」的版本：

- 该版本的 trx_id 是我自己 → 可见
- trx_id 在我的 ReadView 生成之前就已提交 → 可见
- trx_id 属于生成 ReadView 时还活跃的事务 → 不可见，继续往下找

**RR 和 RC 的差别就在 ReadView 的生成时机**：

- **RR**：事务里**第一次快照读**时生成，整个事务复用 → 所以两次读结果一样（可重复读）
- **RC**：**每次快照读**都重新生成 → 所以能看到别人新提交的（不可重复读）

这一条就是两个级别行为差异的全部来源，不用单独记。

**快照读 vs 当前读**是必须分清的一对：

```sql
-- 快照读：走 MVCC，不加锁
SELECT * FROM t WHERE id = 1;

-- 当前读：读最新版本并加锁
SELECT * FROM t WHERE id = 1 FOR UPDATE;      -- 排他锁
SELECT * FROM t WHERE id = 1 LOCK IN SHARE MODE;  -- 共享锁（8.0 推荐 FOR SHARE）
UPDATE / DELETE / INSERT                       -- 全是当前读
```

**所有写操作都是当前读**——必须基于最新数据改，否则就丢更新了。这解释了上一节那个「UPDATE 之后突然看见新行」的现象。

**MVCC 的代价是 undo log 会堆积。** 一个长事务持有旧 ReadView，它需要的旧版本就不能清理（purge）。现象：`information_schema.innodb_metrics` 里 undo 相关指标持续增长、ibdata 或 undo 表空间体积膨胀、历史链表长度（`History list length`，在 `SHOW ENGINE INNODB STATUS` 里）到几十万甚至上百万。这是长事务最主要的危害之一。

# SQL（MySQL 8.0 / InnoDB） > 事务与并发控制 > 锁的种类

来源：https://fqx.lx.ci/sql-map/

按粒度分：

- **表锁** —— 锁整张表。MyISAM 只有表锁；InnoDB 里 DDL 和显式 `LOCK TABLES` 会用
- **行锁** —— 锁具体的行。InnoDB 的主力，**但它锁的是索引记录，不是「行」这个概念**

第二句是关键：**InnoDB 的行锁加在索引上。没有可用索引时，等于把全表的记录都锁了。**

```sql
-- name 上没索引
UPDATE t SET v = 1 WHERE name = 'x';   -- 全表扫描 → 所有行都被锁
```

现象：一条只该影响一行的 UPDATE 把整张表堵住，其他事务全在等锁，超时后报 `Lock wait timeout exceeded; try restarting transaction`。**这是「更新语句要走索引」的真正理由**——不只是快，是不锁全表。

按性质分：

| 锁 | 含义 | 谁能同时持有 |
|---|---|---|
| 共享锁 S | 读锁 | 多个 S 可共存 |
| 排他锁 X | 写锁 | 独占 |
| 意向锁 IS/IX | 表级标记「表里有行被 S/X 锁了」 | 互相兼容 |

**意向锁的作用是让表锁快速判断冲突**：要加表级 X 锁时，不用逐行检查有没有行锁，看有没有 IX 意向锁就行。它是优化手段，业务上不用管。

按范围分（InnoDB RR 级别特有）：

- **记录锁** —— 只锁存在的那条记录
- **间隙锁 Gap Lock** —— 锁两条记录之间的空隙，**防止插入**
- **临键锁 Next-Key Lock** —— 记录锁 + 前面的间隙，是 RR 下的**默认形式**

```sql
-- 表里 id 有 1, 5, 10
SELECT * FROM t WHERE id BETWEEN 5 AND 10 FOR UPDATE;
-- 锁住 (1,5]、(5,10]，所以 id=3 或 id=7 都插不进来
```

间隙锁只在 RR 下存在，RC 下退化成记录锁。这是「RC 并发更好、死锁更少」的原因，也是「RC 下幻读回来了」的原因。

**间隙锁的坑**：它锁的范围比你想的大，且**唯一索引等值命中时会退化成记录锁**（不需要防插入），但等值没命中、或走非唯一索引时会保留间隙锁。所以「明明只更新一行，怎么把别人的插入堵住了」通常是间隙锁。

# SQL（MySQL 8.0 / InnoDB） > 事务与并发控制 > 锁的种类 > 死锁：怎么产生、怎么查、怎么避免

来源：https://fqx.lx.ci/sql-map/

**死锁是两个事务各持有对方要的锁，互相等**。最简单的形态：

```sql
-- 事务 A                        -- 事务 B
UPDATE t SET v=1 WHERE id=1;    UPDATE t SET v=1 WHERE id=2;
UPDATE t SET v=1 WHERE id=2;    UPDATE t SET v=1 WHERE id=1;
-- A 等 B 的 id=2               -- B 等 A 的 id=1
```

InnoDB 有死锁检测，会**主动回滚其中一个**（挑 undo 量小的），报 `Deadlock found when trying to get lock; try restarting transaction`。所以死锁不会一直挂着，但业务会看到偶发失败。

**怎么查**：

```sql
-- 最近一次死锁的完整信息（两个事务各持有什么、在等什么）
SHOW ENGINE INNODB STATUS;      -- 看 LATEST DETECTED DEADLOCK 段

-- 当前锁等待（MySQL 8）
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;

-- 把死锁日志持续记到 error log（生产上建议开）
SET GLOBAL innodb_print_all_deadlocks = ON;
```

只看 `SHOW ENGINE INNODB STATUS` 的问题是它**只保留最近一次**，出事后再去看往往已经被新的覆盖了，所以 `innodb_print_all_deadlocks` 该提前开。

**怎么避免**，按有效性排序：

1. **固定加锁顺序** —— 最有效。批量更新时先按主键排序再逐个更新，所有事务都按同一顺序拿锁，环就成不了
2. **缩短事务** —— 持锁时间短，撞上的概率低
3. **让更新走索引** —— 避免锁范围失控（上一节）
4. **降到 RC** —— 去掉间隙锁，减少一大类死锁
5. **业务上重试** —— 死锁是可重试错误，捕获后重试一次通常就过了。但要保证操作幂等

**批量插入引发死锁**是个常见但不直观的形态：多个事务用 `INSERT ... ON DUPLICATE KEY UPDATE` 插入互相交叉的键集合，加锁顺序不同就会死锁。修法还是排序——插入前把数据按唯一键排好。

# SQL（MySQL 8.0 / InnoDB） > 事务与并发控制 > 长事务的危害

来源：https://fqx.lx.ci/sql-map/

长事务是指开着不提交、跑很久的事务。它的危害是复合的：

**一、undo log 堆不掉。** 长事务持有旧 ReadView，purge 线程不能清理它可能需要的旧版本。现象是 `History list length` 持续增长、undo 表空间膨胀。极端情况下磁盘被 undo 撑满。

**二、锁持有时间长。** 事务里加的行锁/间隙锁到提交才释放，期间其他事务全在等。现象是大量 `Lock wait timeout`，而慢查询日志里可能一条慢 SQL 都没有——阻塞方的等待不算它自己慢。

**三、主从延迟。** 大事务提交时 binlog 一次性写入并传给从库，从库回放期间延迟飙升。一个改十万行的事务能让从库延迟几十秒。

**四、回滚极慢。** 回滚要反向执行所有 undo，改了十万行的事务回滚时间可能比执行还长，期间还持着锁。

**怎么找出长事务**：

```sql
-- 运行超过 60 秒的事务
SELECT trx_id, trx_started, trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60;
```

**最常见的三个来源**：

- **代码里把外部调用放进了事务** —— 开了事务之后去调 HTTP 接口、发消息、调模型 API。几十秒的外部调用把连接和锁一起占住。**这是应用层最典型的架构错误**
- **忘了提交** —— 手动管理事务时某个分支没走到 commit/rollback，或者用了 autocommit=0 的连接又没提交
- **批量操作一个事务干完** —— 一次 UPDATE 百万行。要拆成小批，每批几千行提交一次

**防线**：`innodb_lock_wait_timeout`（等锁超时，默认 50 秒）限制等待方；应用层给事务设超时；加监控告警长事务。事务的正确写法是**只包住数据库操作，外部调用一律挪出去**：先在短事务里落一条「处理中」记录并提交，事务外调外部服务，拿到结果再开一个短事务更新状态。
