# 前端 > JavaScript 核心 > 作用域与闭包：不是「函数里的函数」

来源：https://fqx.lx.ci/frontend-map/

**闭包的准确定义**：函数和它**词法作用域**的组合。函数记住的是它**定义时**所在的作用域，不是调用时的。

```js
function outer() {
  let count = 0;
  return function inner() {
    return ++count;      // inner 记住了 outer 的作用域
  };
}
const f = outer();
f(); // 1
f(); // 2   ← count 没被回收，因为 inner 还引用着它
```

**为什么会存在**：JS 用词法作用域（静态作用域）——一个变量指向谁，看代码写在哪，而不是运行时在哪被调用。这个选择让代码可静态分析，代价是变量的生命周期可能超出函数执行期。

**经典循环陷阱，以及三种解法**：

```js
// ✗ 输出 3 3 3
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));
}

// ✓ 解法1：let 有块级作用域，每轮迭代一个新绑定
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));   // 0 1 2
}

// ✓ 解法2：IIFE 手工造作用域（ES5 时代的写法）
for (var i = 0; i < 3; i++) {
  (function(j) { setTimeout(() => console.log(j)); })(i);
}

// ✓ 解法3：setTimeout 的第三个参数
for (var i = 0; i < 3; i++) {
  setTimeout(console.log, 0, i);
}
```

**`var` / `let` / `const` 的三个维度差异**：

| | 作用域 | 提升 | 重复声明 |
|---|---|---|---|
| `var` | 函数级 | 提升并初始化为 undefined | 允许 |
| `let` | 块级 | 提升但不初始化（TDZ） | 报错 |
| `const` | 块级 | 同 let | 报错 |

**TDZ（暂时性死区）不是「没提升」**——变量确实提升了，只是在声明语句执行前访问会抛 `ReferenceError`。这是刻意设计的：让「用了未声明的变量」变成显式错误，而不是静默的 `undefined`。

**闭包导致的内存泄漏，实际形态**：

```js
function attach() {
  const bigData = new Array(1e6).fill('x');   // 大对象
  document.getElementById('btn').onclick = () => {
    console.log('clicked');                    // 没用到 bigData，但…
  };
}
```

在多数引擎里，闭包捕获的是**整个作用域对象**而非单个变量，所以 `bigData` 可能一直存活。V8 有优化能只保留用到的变量，但**跨浏览器不能依赖**。稳妥做法是不用的大对象手动置 `null`，或者把它挪到闭包外面。

# 前端 > JavaScript 核心 > 作用域与闭包：不是「函数里的函数」 > 闭包的实际用途

来源：https://fqx.lx.ci/frontend-map/

**1. 数据私有化**（模块模式的基础）：

```js
const counter = (() => {
  let n = 0;                       // 外部拿不到
  return { inc: () => ++n, get: () => n };
})();
```

**2. 函数工厂 / 偏函数应用**：

```js
const multiply = a => b => a * b;
const double = multiply(2);
```

**3. 防抖与节流**（面试高频手写题）：

```js
// 防抖：停止触发 delay 毫秒后才执行。搜索框输入、窗口 resize
function debounce(fn, delay) {
  let timer = null;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

// 节流：delay 毫秒内最多执行一次。滚动加载、拖拽
function throttle(fn, delay) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= delay) {
      last = now;
      fn.apply(this, args);
    }
  };
}
```

**手写时的加分点**：
- 用 `fn.apply(this, args)` 而不是 `fn(...args)`——保留调用方的 `this`
- 返回的函数用 `function` 而非箭头函数——否则 `this` 绑死在定义处
- 防抖要提供 `cancel()` 方法，组件卸载时清掉定时器
- 追问会是「防抖要不要支持首次立即执行」（`immediate` 选项）

**React 里的对应物**：`useCallback` 缓存函数、`useRef` 存可变值不触发重渲染——本质都是闭包问题的框架化解法。**stale closure（陈旧闭包）** 是 hooks 最常见的 bug：`useEffect` 的依赖数组漏了变量，回调里读到的是旧值。

# 前端 > JavaScript 核心 > 原型链：JS 的继承是「委托」不是「复制」

来源：https://fqx.lx.ci/frontend-map/

**三个概念别混**：

```
实例.__proto__  ===  构造函数.prototype
构造函数.prototype.constructor  ===  构造函数
```

```js
function Dog(name) { this.name = name; }
Dog.prototype.bark = function () { return this.name + ' woof'; };

const d = new Dog('a');
d.bark();                              // 自身没有 bark，沿 __proto__ 找到
d.__proto__ === Dog.prototype;         // true
Object.getPrototypeOf(d) === Dog.prototype;  // true（推荐写法）
```

**完整链条**：
```
d → Dog.prototype → Object.prototype → null
```

**`new` 做了四件事**（手写 `new` 是常见题）：

```js
function myNew(Ctor, ...args) {
  const obj = Object.create(Ctor.prototype);   // 1. 创建对象，原型指向 Ctor.prototype
  const ret = Ctor.apply(obj, args);           // 2. 以 obj 为 this 执行构造函数
  return (ret !== null && typeof ret === 'object') ? ret : obj;  // 3+4. 返回对象则用它，否则用 obj
}
```

第 3 步那个判断是易错点：**构造函数显式返回对象时，`new` 的结果是那个对象**；返回原始值则忽略。

**`class` 是语法糖，但有三个真实差异**：
1. 类声明不提升可用（在 TDZ 里），`function` 可以先调用后声明
2. 类内部强制严格模式
3. 类方法不可枚举（`for...in` 遍历不到），而 `Prototype.method = ...` 可枚举

**`instanceof` 的原理和局限**：

```js
function myInstanceof(obj, Ctor) {
  let proto = Object.getPrototypeOf(obj);
  while (proto) {
    if (proto === Ctor.prototype) return true;
    proto = Object.getPrototypeOf(proto);
  }
  return false;
}
```

**局限**：跨 iframe / 跨 realm 时失效——两个窗口有各自的 `Array`，A 窗口的数组 `instanceof` B 窗口的 `Array` 是 `false`。判断类型稳妥用 `Array.isArray()` 或 `Object.prototype.toString.call(x)`。

**属性查找的坑**：`in` 会查原型链，`hasOwnProperty` 只查自身。现代写法用 `Object.hasOwn(obj, key)`（ES2022），比 `obj.hasOwnProperty(key)` 安全——后者在 `obj` 是 `Object.create(null)` 或自己有个叫 hasOwnProperty 的属性时会炸。

# 前端 > JavaScript 核心 > this：由「怎么调用」决定，不是「在哪定义」

来源：https://fqx.lx.ci/frontend-map/

**五条规则，从高到低优先级**：

```js
new Fn()                    // 1. new 绑定 → this 是新对象
fn.call(o) / apply / bind   // 2. 显式绑定 → this 是 o
o.fn()                      // 3. 隐式绑定 → this 是 o
fn()                        // 4. 默认绑定 → 非严格模式是 globalThis，严格模式是 undefined
() => {}                    // 5. 箭头函数 → 没有自己的 this，取定义时外层的
```

**箭头函数不是「this 指向外层」，是「根本没有 this」**——它连 `arguments`、`super`、`new.target` 都没有，也不能 `new`。查 `this` 时直接跳到外层作用域找。所以 `bind`/`call` 对箭头函数无效。

**最常见的丢 this 场景**：

```js
const obj = {
  name: 'x',
  greet() { return this.name; }
};

const g = obj.greet;
g();                        // undefined —— 赋值时丢了调用对象

setTimeout(obj.greet, 0);   // undefined —— 同上，传的是函数引用

// 三种修法
setTimeout(obj.greet.bind(obj), 0);
setTimeout(() => obj.greet(), 0);
// 或者类里用属性初始化器：greet = () => this.name
```

**记住这个判断法**：看调用那一刻**函数左边的点前面是谁**。没有点就是默认绑定。

**`bind` 的三个细节**：
- 返回新函数，多次 bind 只有第一次生效
- `bind` 后的函数仍可 `new`，此时 `this` 是新对象（new 优先级最高）
- 支持柯里化：`fn.bind(o, a)` 预置参数

**`call` 和 `apply` 只差参数形式**：`call(o, a, b)` vs `apply(o, [a, b])`。ES6 后 `apply` 用得少了，`fn(...arr)` 更直观。

**手写 bind 的完整版**（面试要求能处理 new）：

```js
Function.prototype.myBind = function (ctx, ...preArgs) {
  const fn = this;
  function bound(...args) {
    // 被 new 调用时忽略 ctx
    return fn.apply(this instanceof bound ? this : ctx, [...preArgs, ...args]);
  }
  bound.prototype = Object.create(fn.prototype);
  return bound;
};
```

# 前端 > JavaScript 核心 > 事件循环：微任务、宏任务与渲染时机

来源：https://fqx.lx.ci/frontend-map/

**一轮循环的顺序**：

```
执行同步代码（一个宏任务）
  ↓
清空微任务队列（全部执行完，包括执行中新产生的）
  ↓
（可能）渲染一帧
  ↓
取下一个宏任务
```

**分类**：
- **宏任务**：`setTimeout`、`setInterval`、`setImmediate`(Node)、I/O、UI 事件、`MessageChannel`
- **微任务**：`Promise.then/catch/finally`、`queueMicrotask`、`MutationObserver`、`await` 之后的代码

**必考输出题**：

```js
console.log('1');
setTimeout(() => console.log('2'));
Promise.resolve().then(() => console.log('3'));
console.log('4');
// 输出 1 4 3 2
```

**加上 async/await 的版本**：

```js
async function a() {
  console.log('a1');
  await b();            // await 后面的代码等价于 .then 里的回调 → 微任务
  console.log('a2');
}
async function b() { console.log('b'); }

console.log('start');
a();
Promise.resolve().then(() => console.log('p'));
console.log('end');

// start → a1 → b → end → a2 → p
```

**关键**：`await` 会**立即执行**右边的表达式（所以 `b` 同步打印），然后把**后续代码**包成微任务。

**微任务饥饿是真实的性能问题**：

```js
function loop() { Promise.resolve().then(loop); }
loop();   // 页面彻底卡死 —— 微任务队列永远清不空，渲染永远轮不到
```

换成 `setTimeout(loop)` 就不会卡死——每轮之间浏览器有机会渲染。**所以要让出主线程做长任务分片，必须用宏任务**（`setTimeout` 或 `scheduler.postTask`），微任务不行。

**`requestAnimationFrame` 不在这两类里**——它在渲染前执行，一帧一次。做动画用它，不用 `setTimeout(16)`：后者跟屏幕刷新不同步会掉帧。

**`requestIdleCallback`** 在浏览器空闲时执行，适合非紧急任务（预加载、上报），但 Safari 至今不支持，要 polyfill。

**Node 和浏览器的差异**：Node 的事件循环有六个阶段（timers / pending / poll / check / close），`process.nextTick` 优先级高于 Promise 微任务。Node 11 之前微任务的清空时机和浏览器不一致，之后对齐了。

# 前端 > JavaScript 核心 > Promise 与异步控制

来源：https://fqx.lx.ci/frontend-map/

**Promise 的三个状态不可逆**：pending → fulfilled / rejected。已定型后再调 resolve/reject 无效。

**四个组合方法，别记混**：

```js
Promise.all([...])          // 全部成功才成功，一个失败立刻失败（fail-fast）
Promise.allSettled([...])   // 等全部结束，返回 {status, value/reason} 数组，永不 reject
Promise.race([...])         // 第一个定型的（成功或失败）胜出
Promise.any([...])          // 第一个成功的胜出，全失败才 reject（AggregateError）
```

**实际选择**：
- 并发请求、缺一不可 → `all`
- 并发请求、部分失败可接受（批量上传） → `allSettled`
- 超时控制 → `race`（配一个定时 reject 的 promise）
- 多个镜像源取最快的 → `any`

**`Promise.all` 的坑**：它 fail-fast，但**其他请求不会被取消**——它们继续跑完，只是结果被忽略。要真取消得配 `AbortController`。

**超时封装**（常见手写题）：

```js
function withTimeout(promise, ms) {
  const ctrl = new AbortController();
  const timeout = new Promise((_, rej) =>
    setTimeout(() => { ctrl.abort(); rej(new Error('timeout')); }, ms)
  );
  return Promise.race([promise, timeout]);
}
```

**并发限流**（比防抖节流更能区分水平的题）：

```js
async function pMap(items, fn, limit = 5) {
  const results = [];
  const executing = new Set();
  for (const [i, item] of items.entries()) {
    const p = Promise.resolve().then(() => fn(item, i));
    results.push(p);
    executing.add(p);
    p.finally(() => executing.delete(p));
    if (executing.size >= limit) await Promise.race(executing);
  }
  return Promise.all(results);
}
```

**错误处理三个易错点**：

```js
// 1. 忘记 return，链断了
p.then(() => { doAsync(); })        // ✗ 后面的 then 不等它
p.then(() => doAsync())             // ✓

// 2. catch 位置。放中间只能捕获它之前的
p.then(a).catch(h).then(b)          // b 的错误没人管
p.then(a).then(b).catch(h)          // ✓

// 3. async 函数里的同步 throw 也变成 rejected promise
async function f() { throw new Error('x'); }
f();                                 // 未处理的 rejection，不是同步异常
```

**`for await...of` 是串行的**，不是并行：

```js
// ✗ 串行，总耗时 = 各项之和
for (const url of urls) { await fetch(url); }

// ✓ 并行
await Promise.all(urls.map(u => fetch(u)));
```

这个「看起来在用异步其实是同步等待」的错误在代码审查里非常常见。
