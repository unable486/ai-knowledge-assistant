## Agent 工程实现（简历高频词的兑付层）

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > Agent 执行循环具体怎么实现

一个 while 循环，每轮把「完整对话历史 + 工具 schema 列表」发给模型，看返回类型分流：返回纯文本就结束循环；返回 `tool_calls` 就执行工具、把结果以 `role: "tool"` 追加进历史、进下一轮。历史是累积的，所以第 N 轮模型能看到前面所有工具的输入输出。

 

四个必须自己处理的地方，缺一个就会在线上暴露：

 

- **终止条件**：除了「模型返回文本」，还要有最大轮次上限。模型可能反复调同一个工具不收敛，没有上限就是无限账单。
- **并行工具调用**：一轮里模型可能返回多个 `tool_calls`。无依赖的要并发执行再一起塞回，串行做会让延迟翻几倍。
- **工具报错也要回灌**：工具抛异常时，把错误信息当作工具结果返回给模型，让它自己决定改参数重试还是换路子。直接把异常抛给用户，等于放弃了 Agent 的自愈能力。
- **消息角色严格交替**：`assistant` 发起的 `tool_calls`，每一个 `tool_call_id` 都必须有对应的 `tool` 消息回应，缺一条整个请求会被 API 拒绝。

 

上下文会随轮次线性膨胀，这是 Agent 成本的主要来源 —— 一个 20 轮的任务，第 20 次调用要把前 19 轮的工具输出全部重发一遍。所以要么压缩历史，要么把大块工具输出落盘只回灌摘要。

 

**追问「你的循环跑到第几轮会失控，怎么发现的」**：说得出具体轮次和现象才算做过。典型答案是「工具返回了一个几万字符的结果，第 8 轮开始每次请求都是 9 万 token，延迟从 3 秒涨到 40 秒」，对应的修法是超过阈值的工具输出写文件、只回灌路径和前 200 字。答不出具体数字就是没上线过。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > 上百个工具/Skills，怎么让模型选对

不能全塞进 context —— 100 个工具的完整 schema 轻松上万 token，每轮都发一遍，而且选项越多模型越容易选错。

 

两级加载是标准做法：系统提示里只放「名字 + 一句话触发条件」的清单，模型判断相关了再调一个 `load_tool` / `read_skill` 把完整说明取回来。代价是多一轮往返，收益是 context 从上万降到几百 token。

 

让「选对」这件事真正成立，靠的是描述而不是数量：

 

- **描述写触发条件，不写功能**。「Use when \<什么情况\>」比「一个查询天气的工具」有用得多 —— 模型是在做匹配，不是在读产品手册。
- **前 50 个字符决定命中率**。清单里通常只截断显示开头，触发词必须前置。
- **重叠的工具要写清边界**。两个功能相近的工具，各自的描述里要点明「什么时候该用另一个」，否则模型会随机挑。
- **分组或按场景过滤**。当前任务明显只涉及某一类时，只暴露那一组。

 

评估方式是建一个「问题 → 应该选哪个工具」的标注集，跑准确率。没有这个集合，「选得准」就只是感觉。

 

**追问「工具数量从 20 涨到 100，选择准确率掉了多少」**：这题的价值在于承认存在退化。诚实的答案是「掉了，尤其是描述相近的那几个」，然后给出你的应对 —— 合并近似工具、重写触发词、或者按场景分组。回答「没影响」的候选人，通常是没测过。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > 语义缓存命中率 99% 可信吗

不可信，这个数字本身就是要被追问的地方。

 

语义缓存的原理是把问题转成向量，新问题进来先算相似度，超过阈值就直接返回缓存答案。真实业务里的命中率通常在 **30%–60%** —— 用户问法千变万化，能被判定为「语义相同」的比例有限。

 

99% 只有三种解释：

 

- **请求高度重复**。比如固定几个模板化的定时任务在跑。这时候高命中率是业务特征，不是技术成果，说出来反而暴露场景单一。
- **相似度阈值定得太松**。阈值降到 0.7 命中率会飙升，代价是「北京今天天气」和「上海明天天气」被判成同一个问题，返回错答案。命中率和错答率是一组此消彼长的指标，只报前者等于没报。
- **统计口径把不该算的算进去了**。最常见的是把「prompt 前缀缓存」（provider 侧对相同前缀 token 的复用，是计费优化）和「语义缓存」（跳过整次调用）混成一个数。前者命中率确实能到 90% 以上，但它省的是钱不是调用。

 

所以被问到时，正确的答法是先说口径：命中率的分母是什么、阈值多少、错答率是多少、有没有做人工抽检。**报单一数字不报口径，面试官会认为你没参与实际度量。**

 

**追问「阈值调低 0.05，命中率和错答率各变多少」**：这题只有真跑过 A/B 的人答得出。要能说出「阈值从 0.85 降到 0.80，命中率涨了 12 个点，但抽检发现 3% 的答案答的是相邻问题，最后收回到 0.83」这种带回退过程的答案。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > ReAct 和 Plan-and-Execute 怎么选

ReAct 是边想边做：每轮让模型输出「思考 → 动作」，看到结果再决定下一步。Plan-and-Execute 是先出完整计划，再逐条执行。

 

选择依据是**任务的步骤能不能提前确定**：

 

- 探索型任务（排查线上问题、在陌生代码库里找东西）用 ReAct。计划在第二步就会因为看到实际情况而作废，提前规划是浪费。
- 步骤固定的流水线（文档批处理、多阶段内容生成）用 Plan-and-Execute。计划可以校验、可以给人审、失败能从断点续跑。
- 长任务常混用：先出粗粒度计划，每一步内部用 ReAct 展开。

 

各自的失效方式要说得出来：ReAct 容易在两个动作间反复摆动不收敛（A 查不到查 B，B 查不到又回 A），需要给最大轮次和「重复动作检测」。Plan-and-Execute 的问题是计划一旦基于错误假设，后面每一步都在错误方向上执行，所以每步执行完要校验前提是否还成立，不成立就重新规划。

 

**追问「你的 Agent 在什么情况下会来回打转，怎么止住的」**：答案要具体到检测手段 —— 比如记录最近 N 轮的 (工具名, 参数) 指纹，重复出现就强制让模型换策略或直接终止。答「加了最大轮次」只是兜底，不是解法。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > 「成功率从 45% 提到 82%」这个数怎么来的

这类数字是简历里最容易被拆的地方，因为它需要四个前提同时成立，缺一个数字就不成立。

 

**成功的定义谁给的**。是规则判定（有没有产出、格式合不合法）、模型判定（LLM-as-judge）、还是人工标注？三种口径的绝对值差很远。模型判定还要说清 judge 用的哪个模型、和人工标注的一致率是多少 —— 一致率没测过，82% 就是另一个模型的主观分。

 

**样本是多少、怎么抽的**。50 条和 5000 条的置信区间完全不同。抽样方式更关键：如果 45% 是早期真实流量、82% 是后来自己挑的测试集，两个数没有可比性。

 

**有没有对照组**。中间可能同时换了模型、改了 prompt、加了检索。不做变量隔离就说不出提升来自哪一项，面试官追问「哪一步贡献最大」就答不上。

 

**基线怎么测的**。45% 是上线前实测的，还是事后回忆的？回忆值不能当基线。

 

诚实的表述方式是把口径写进句子：「在 300 条人工标注的测试集上，首条产出通过审核的比例从 45% 提升到 82%，主要来自检索召回改进（贡献约 20 个点）和输出 schema 约束（约 12 个点）」。**这样说反而更有分量 —— 它证明你参与了度量，不只是拿到了一个结论。**

 

**追问「这 300 条测试集里，改动之后新挂掉的有几条」**：真做过评估的人一定见过「整体涨了但某类退化」的情况。答得出「有 7 条原来对的变错了，都是长文档的场景，因为分块变小之后上下文断了」，可信度立刻不一样。答「全都变好了」基本等于没做过对比。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > 多个 LLM 供应商怎么接入和切换

抽一层统一的调用接口，把差异关在适配器里，业务代码只认自己的抽象。需要处理的差异比想象的多：

 

- **协议形状**。OpenAI 的 chat completions、Anthropic 的 messages、以及各家的推理字段（`reasoning_content` 之类）结构都不同。
- **工具调用格式**。参数是 JSON 字符串还是对象、流式下增量怎么拼、`finish_reason` 叫什么，各家不一致。
- **计费口径**。有的把缓存命中的 token 单独计价，有的不区分，成本核算要按供应商分别算。
- **失败语义**。同一个 429 可能是限流（该退避重试）也可能是余额耗尽（重试无意义），要按供应商映射成自己的错误类型再决定重试策略。

 

切换机制上，主用一家 + 失败降级到备用是最小可用形态。三个坑：

 

**降级链只对特定错误生效**。限流、5xx、连接错误该降级；但「HTTP 200 但流是空的」这种不会触发任何重试逻辑，请求会一直挂着 —— 这是实际会遇到的最难查的一类。

 

**能力不是按供应商而是按模型**。同一家、同一个 key、同一分钟，模型 A 流式非流式都通，模型 B 只有流式能用，模型 C 直接无可用通道。所以不能因为一个模型能用就推断同家的其他模型能用。

 

**降级会静默改变行为**。备用模型的能力和风格不同，用户会感觉到「今天回答变差了」却找不到原因。所以每次调用要记录实际使用的供应商和模型，否则事后无法归因。

 

**追问「切到备用之后，怎么知道自己切了」**：答案是可观测性 —— 每次调用落一条含供应商、模型、token、延迟的日志，异常降级发告警。说不出记录了什么字段，就说明线上出问题时只能靠猜。

 

## 飞书直播高频题补充

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > SDD 是什么，为什么能降低 AI Coding 的不确定性

这里的 SDD 指 Specification-Driven Development（规格驱动开发）：先把需求变成可审查的规格，再从规格拆计划和任务，最后让 Agent 按任务实施并验证。最小链路是 `spec → plan → tasks → implement → verify`。

 

它不是「把 prompt 写长一点」。一次性告诉模型“把系统重构好”，模型会自己补齐缺失前提，改动范围不可控；SDD 把不确定性拆到几个可检查的产物里：

 

- **spec** 定义目标、非目标、接口契约和验收标准，防止模型做偏。
- **plan** 定义改哪些模块、顺序和风险，防止模型边写边临时发明架构。
- **tasks** 把工作切成单个上下文窗口能完成的小任务，每项都有输入、输出和完成条件。
- **verify** 用测试、类型检查、构建和真实调用证明完成，而不是相信 Agent 说“已完成”。

 

代价是前期写规格变慢；小修复没必要全套上，跨模块改造、迁移、AI 生成代码这类高风险任务才值得。

 

**追问「spec 写到什么粒度才不会变成另一份代码」**：写行为和约束，不写逐行实现。比如写“并发请求只刷新一次 token，失败后所有等待请求收到同一个错误”，不要把 Promise 队列实现提前写死。验收标准应能自动验证，否则只是愿望。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > Harness Engineering 是什么，和 Agent 有什么关系

LLM 只负责生成和判断，Harness（执行框架）负责把它约束成可靠系统。可以把 Agent 看成：

 

`LLM + 指令/规则 + Skills + Tools/MCP + 上下文管理 + 记忆 + 权限 + 测试验证 + 可观测性`

 

Harness Engineering 就是设计后面这些工程设施。没有 Harness，模型只能“建议你怎么做”；有了工具和循环，它能实际执行；再加权限、预算、终止条件和验证，它才敢在生产环境里执行。

 

一个代码 Agent 的 Harness 至少要处理：工作目录和文件权限、命令白名单、变更 diff、最大轮次和 token 预算、测试/构建门禁、失败重试、日志与回滚。效果不只看最终答案，还看成功率、平均轮次、工具失败率、成本和造成破坏性改动的比例。

 

**追问「你给 Hermes 加一个新能力，改模型还是改 Harness」**：多数业务能力先改 Harness。例如“会查邮件”是加邮件工具和权限，不是微调模型；“总在错误目录运行命令”是补工作目录约束和验证。只有模型本身无法理解或推理时才考虑换模型或训练。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > 上下文超过 context window 怎么处理

不能等 API 报超限再截掉最早消息。先把上下文分层：必须常驻的 system/安全规则，当前任务状态，最近对话，历史摘要，以及可按需读取的文件或工具输出。

 

处理顺序通常是：

 

1. 工具返回的大文本落盘，只回灌路径、摘要和关键片段。
2. 历史对话做结构化压缩，保留决策、未完成事项、错误和精确标识符，而不是只写一段泛化摘要。
3. 用滑动窗口保留最近若干轮；被摘要覆盖的原文退出活跃上下文。
4. 长任务按 SDD 拆成小任务，每个窗口只完成一项，用文件或任务状态跨窗口交接。
5. 需要旧细节时通过检索按需取回，而不是把整个仓库和全部聊天每轮重发。

 

压缩有信息损失，所以摘要也要验证：文件路径、命令、数字、失败原因最容易被改写错。Agent 成本不是只由当前输出决定，20 轮循环会反复重发前 19 轮，输入成本近似二次增长。

 

**追问「哪些内容绝对不能被摘要改写」**：API key 不能进上下文本身；除此之外，工具调用 ID、错误原文、文件路径、版本号、用户明确约束和未完成验收条件必须原样保留。摘要后用这些字段做一致性检查。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > Skill 里应该沉淀什么，怎么验证它真的有效

Skill 沉淀的是可复用的**决策过程和操作契约**，不是把一段聊天记录存下来。应该包含：什么时候触发、何时不该用、前置条件、可靠步骤、输入输出格式、已知坑和完成验证。

 

以“Vue 到 React 迁移”为例，Skill 不该只写“把 computed 改成 useMemo”，而要写组件分类、状态映射、路由/权限迁移顺序、每批迁移后的类型检查和视觉回归，以及哪些复杂组件必须人工审查。

 

验证不能看 Skill 数量，要建“任务 → 应加载哪个 Skill”的选择集和执行回归集：比较加载前后的成功率、轮次、token、返工次数，并检查错误 Skill 是否被误触发。Skill 过多且描述重叠时，选择准确率会下降。

 

**追问「什么内容不该写进 Skill」**：一周后就过期的任务进度、密钥、具体客户数据、只对一次故障有效的日志都不该写。稳定事实放配置或文档，临时状态放任务记录；Skill 只留可跨任务复用的方法。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > Agent 为什么需要 Tool Calling

LLM 只能根据上下文生成 token，不能天然读取实时数据库、调用业务接口或证明自己真的改了文件。Tool Calling 把“模型表达意图”和“系统执行动作”分开：模型按 schema 选择工具和参数，宿主程序校验权限后执行，再把结果回灌给模型。

 

这层分离带来三件事：

 

- **实时性**：查天气、库存、用户信息时读取真实系统，而不是靠训练数据猜。
- **可执行性**：能发请求、写文件、跑测试，Agent 才不只是聊天机器人。
- **可治理性**：参数可校验、权限可限制、调用可审计，高风险动作可要求人工确认。

 

Tool Calling 不等于 MCP。前者是模型输出结构化调用意图的机制；MCP 是工具发现、描述和调用的标准协议。一个本地函数也能被 Tool Calling 调用，不需要 MCP。

 

**追问「模型传了 `deleteAll: true` 怎么办」**：不能因为 schema 合法就执行。宿主侧还要做业务校验、身份鉴权、租户隔离、影响范围计算和高风险确认；模型永远不是授权主体。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > LangChain 和 LangGraph 分别解决什么问题

LangChain 提供模型、Prompt、Retriever、Tool、Output Parser 等组件及组合接口，适合把一条调用链快速串起来。LangGraph 在其上强调“有状态的图”：节点、条件边、循环、checkpoint、暂停恢复和人工介入，适合长流程 Agent。

 

简单 RAG（改写 → 检索 → 重排 → 生成）用普通函数或 LangChain 就够；需要失败回到上一步、等待审批、断点续跑、多个分支汇合时，LangGraph 的状态机更合适。

 

框架的代价是抽象层遮住真实协议、调试栈变长、版本变化快。你能用十几行原生代码写清的 Agent 循环，不应为了“用了框架”强行上 LangGraph。选型依据是状态和流程复杂度，不是流行度。

 

**追问「不用 LangGraph 怎么实现断点续跑」**：把每个节点的输入、输出、状态和幂等键持久化；恢复时从最后一个已验证节点继续。能讲清这个，才说明理解的是机制而不是 API。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > Chatbot、Workflow、Agent 有什么区别

- **Chatbot**：主要做对话和生成，流程通常是一问一答，最多带检索或固定工具。
- **Workflow**：步骤由开发者预先确定，模型只负责其中某些节点；确定性强、易测试、易审计。
- **Agent**：模型根据目标和中间结果动态决定下一步调用什么工具、何时停止，适合路径无法提前写死的任务。

 

选择原则是**能用 Workflow 就不要上 Agent**。固定的“上传合同 → OCR → 提取字段 → 人工审核 → 入库”是 Workflow；“排查为什么服务突然变慢，需要自行查日志、指标和代码”才需要 Agent。

 

Agent 灵活，但成本、延迟、失败空间和安全风险都更大。常见生产形态是外层 Workflow 固定关键控制点，某个探索节点内部允许 Agent 自主行动。

 

**追问「听音分析能不能升级成 Agent 项目」**：先看是否需要动态决策。如果只是上传音频后固定执行转写、分类、报告，就是 Workflow；只有模型要根据结果自主选择降噪、重试、查询知识库或请求人工复核，才有 Agent 的必要。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > AI 修复代码，怎么保证没把项目改坏

不能靠 Review 一眼看着能跑。安全链路应该是：限定范围 → 修改 → 查看 diff → 自动验证 → 行为回归 → 人工审批 → 小范围发布。

 

具体措施包括：只允许修改指定目录；禁止直接改生产配置和迁移历史；每批改动控制规模；运行格式化、类型检查、单元测试、构建和关键 E2E；用基线测试比较改动前后；依赖升级再跑漏洞和许可证扫描；不满足门禁就自动回滚本批改动。

 

AI 最危险的不是语法错，而是“测试通过但业务语义变了”。例如把权限判断删掉后页面能正常渲染，现有单测也可能全绿。因此规格里要明确不变量：权限、金额、幂等、事务和外部接口契约，并为它们补回归用例。

 

**追问「AI 同时改了 80 个文件，你先看什么」**：先拒绝大爆炸式变更，让它按模块拆批；再看依赖和配置、数据库迁移、鉴权、公共 API 这类高影响 diff，最后才看机械格式变化。无法拆分的改动不应自动合并。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > 模型是怎么发现并调用 MCP 服务的

模型不会直接连接 MCP Server。Host（IDE 或 Agent 应用）先通过 stdio、HTTP 等传输连接 Server，调用 MCP 的发现接口拿到工具名称、描述和输入 schema，再把合适的工具以模型能理解的 tools 格式放进请求。

 

模型返回工具调用意图后，Host 校验参数和权限，把调用转发给对应 MCP Server；Server 执行真实 SDK/API，再经 Host 把结果作为 tool 消息回灌。链路是：

 

`用户 → Host → LLM → tool call → Host → MCP Server → 业务系统 → Host → LLM`

 

所以协议只解决互操作，不自动解决权限。Host 仍要决定暴露哪些 Server、哪些工具需要确认、返回内容是否含敏感数据。

 

**追问「接入一个 MCP Server 后模型为什么仍然找不到工具」**：按链路查：Server 是否启动并完成握手，tools/list 是否返回，工具描述是否被 Host 过滤，是否真的放进本次模型请求，模型是否支持工具调用，以及名称/schema 是否清晰。不要直接改 prompt 猜。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > Agent 为什么不能直接写数据库

不是绝对不能，而是不能把数据库连接和任意 SQL 权限直接交给模型。模型输出具有不确定性，又缺少完整业务不变量；一次错误参数可能跨租户更新、绕过校验或造成不可逆删除。

 

正确边界是让 Agent 调用窄的领域工具，例如 `createWorkoutSet(sessionId, exerciseId, reps)`，由业务服务完成鉴权、租户隔离、参数校验、事务、幂等和审计。高风险写入先生成计划或草稿，再由用户确认；批量操作先返回影响行数和样本。

 

只读也不能直接放开全库：要用只读账号、行列权限、查询超时、最大返回行数和脱敏。把自然语言直接拼 SQL 更是注入和越权的双重风险。

 

**追问「Agent 重试导致同一订单写了两次怎么办」**：工具接口必须有幂等键，数据库用唯一约束兜底；Agent 的重试只复用原键，不能每轮重新生成。前端把按钮禁用只能改善体验，不能保证幂等。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > 「AI 出码精准生成率 90%」怎么计算

先拒绝“精准”这个模糊词，定义可复现的通过标准。比较可信的口径是：给定一组真实开发任务，Agent 首次产出的变更在不人工改代码的情况下，同时通过类型检查、测试、构建和任务级验收的比例。

 

分母必须是预先固定的任务集，不能只统计最后做成功的任务；同一个任务重试五次成功，不能算五个成功样本。还要按复杂度分层，因为改文案和跨模块迁移放在一起算，会被简单任务抬高。

 

至少同时报告：首次通过率、最终通过率、平均人工修改量、平均轮次、回归缺陷率和成本。90% 若只是“代码能运行”或“人工 Review 觉得差不多”，不能叫精准生成率。

 

这和第 37 题的统计纪律相同，但对象不同：第 37 题偏 Agent 任务成功率，这题专门约束代码生成的工程验收。

 

**追问「原来通过的任务，改了 Skill 后新挂了多少」**：必须做逐任务 diff。总体从 80% 升到 90%，可能同时有 15 个新修好、5 个旧任务退化；只报净增长会掩盖回归。答不出新挂数量，就没有真正做回归评估。

# 面试 04 · RAG / Agent / 评估 / 成本 / 安全 > AI Coding 你用什么模型，Agent 用什么

这题看着像闲聊，实际在筛两件事：你是不是真的每天在用，以及你有没有「按任务选模型」的成本意识。只报一个模型名字（哪怕报得对）拿不到分，因为那是看新闻也能说的。

 

**能拿分的答法是分层报，并且说清依据。**

 

- **写代码/改代码的主力**：用当前榜单前列的 coding 模型，说清你为什么选它——多文件协同修改的成功率、工具调用（读文件、跑测试、改文件）出错率、以及长上下文里不丢改动。这三样是 agentic coding 真正的瓶颈，不是单文件补全质量。
- **量大且简单的活**（改文案、批量重命名、格式化、写单测骨架）：降级到便宜的中档模型或开源权重模型。这类任务上贵模型的边际收益接近零，而 token 成本差 5~10 倍。
- **规划/架构讨论**：可以用推理更强的那档，但要意识到它慢且贵，适合一次性产出方案文档，不适合塞进每轮循环。
- **Agent 编排层**：一句话说清「模型 ≠ agent」。Agent 是执行循环 + 工具集 + 上下文管理（本文件第 33 题），常见形态是 CLI agent（Claude Code、Codex CLI、OpenCode 这类）或 IDE 内的 agent 模式，模型只是里面可替换的一块。真正决定好不好用的是 harness：工具粒度、diff 应用方式、上下文压缩策略、失败重试（第 40 题）。

 

**不要背具体榜单名次。** 这块每一两个月就翻一次，2026-09 这个时间点上前列基本是 Anthropic Claude Opus 系与 Google Gemini 3.x Pro、OpenAI GPT-5.x 在轮换，开源侧 GLM-5、DeepSeek V3.2、Kimi K2.x、Qwen3.5 咬得很紧。安全的口径是：**说清你用的那个 + 你判断它好用的依据 + 你什么时候会换**，而不是背分数。面试官比你更清楚榜单已经过期。

 

而且要主动提榜单的局限：SWE-bench Verified 是 2023 年的 GitHub issue，存在数据污染，各家报的分还依赖各自的 scaffold（同一个模型换 harness 能差 5~8 个点）。所以更可信的是**你自己的活儿上的对比**：同一批任务在两个模型上跑，比首次通过率、平均返工轮次、总花费（本文件第 49 题的口径）。

 

**追问「你怎么决定一个任务交给 AI 还是自己写」**：这一问是想听你有没有被坑过。可判定的分界是三条：**验收能不能自动化**——有类型检查、有测试、能跑起来看结果的，交给 AI 划算，因为它的错能被机器抓住；只能靠人眼判断对错的（视觉细节、交互手感、性能调优），自己来更快。**上下文是不是可迁移**——写在文档和代码里的规则 AI 能吃到，只存在你脑子里或口头约定里的隐性约束（这个字段线上有脏数据、那个接口不能并发调）它必然违反，除非你先把约束写下来。**错了的代价可不可逆**——改测试、改前端页面错了随时回滚；动数据库迁移、改鉴权、动线上配置，必须自己写自己审（第 48 题的边界）。补一句最能证明你真在用的话：**AI 最大的价值不在写新代码，在读陌生代码和补测试**——这两件事人的意愿最低而机器的准确率最高。
