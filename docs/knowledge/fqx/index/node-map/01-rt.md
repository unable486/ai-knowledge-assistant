这份导图按「运行时 → 模块 → 异步 → 服务 → 运维」的顺序排：**事件循环**解释了 Node 的一切行为特征，**异步编程**是日常写代码的主要形态，**网络与服务端**是实际交付的东西，**调试性能运维**是线上出问题时用的。

每个节点讲三件事：是什么、为什么这么设计、你会踩的坑。坑那部分是重点——Node 的事故大多来自「单线程」这个前提被忽略。

# Node 20 / 22 > 运行时与事件循环

Node = V8（执行 JS）+ libuv（事件循环和线程池）+ 一堆 C++ 绑定。理解事件循环的六个阶段和微任务的插队规则，就能解释「为什么我的 setTimeout(0) 比 setImmediate 晚」「为什么一个同步的 JSON.parse 让整个服务超时」。这块是 Node 性能问题的源头。

# Node 20 / 22 > 运行时与事件循环 > Node 的组成：V8 + libuv

**V8** 负责解析和执行 JS，管堆内存和垃圾回收。它本身不知道什么是文件、什么是 socket。

**libuv** 提供事件循环和跨平台异步 IO。它是 Node 「异步」的真正来源。

**关键区分——两类异步走的路完全不同**：

| 类型 | 实现方式 | 是否占线程池 |
|---|---|---|
| 网络 IO（TCP、HTTP、DNS 部分） | 操作系统的事件通知（epoll/kqueue/IOCP） | **不占** |
| 文件 IO、`crypto.pbkdf2`、`zlib`、`dns.lookup` | **libuv 线程池** | **占** |

**线程池默认只有 4 个线程**（`UV_THREADPOOL_SIZE`，最大 1024）。这解释了一个真实现象：

```js
// 同时发起 5 个大文件读取，第 5 个要等前面某个完成才开始
// 因为线程池被占满了
```

**所以「Node 是单线程」这句话要修正**：**执行 JS 是单线程**（一个主线程跑事件循环），但底层有线程池和 OS 事件机制在并行干活。CPU 密集的 JS 计算才是真的会独占那唯一的 JS 线程。

**调大线程池的场景**：大量文件操作、大量 `crypto` 计算（bcrypt、pbkdf2）、大量 `zlib` 压缩。

```bash
UV_THREADPOOL_SIZE=16 node app.js
```

**必须在第一次用到线程池之前设**（进程启动时读一次），运行时改 `process.env` 无效。

**和 Python 对照**：Python 的 asyncio 也是单线程事件循环，但**Python 没有 Node 这种「所有内置 IO 都自动异步」的设定**——`open().read()` 就是同步的。Node 的标准库默认给你异步版本（`fs.readFile` vs `fs.readFileSync`），心智负担小得多。反过来 Node 的坑是：一不小心用了 `Sync` 结尾的函数，或者写了个纯计算的 for 循环，就把整个服务堵住了。

# Node 20 / 22 > 运行时与事件循环 > 事件循环的六个阶段

每一轮（tick）按固定顺序走六个阶段，每个阶段有自己的回调队列：

```
   ┌───────────────────────────┐
┌─>│         timers            │  setTimeout / setInterval 到期回调
│  ├───────────────────────────┤
│  │     pending callbacks     │  上一轮延迟的系统回调（如某些 TCP 错误）
│  ├───────────────────────────┤
│  │       idle, prepare       │  内部使用
│  ├───────────────────────────┤     ┌───────────────┐
│  │           poll            │<────│  incoming IO  │  等待新 IO 事件，执行其回调
│  ├───────────────────────────┤     └───────────────┘
│  │           check           │  setImmediate 回调
│  ├───────────────────────────┤
└──┤      close callbacks      │  socket.on('close') 之类
   └───────────────────────────┘
```

**日常只需要关心三个**：**timers**、**poll**、**check**。

**poll 阶段是循环的重心**：绝大多数时间花在这里等 IO。它的等待时长由「最近的 timer 还有多久到期」决定——没有 timer 且没有其他待办时，它会一直阻塞等 IO（这就是为什么 Node 进程空闲时 CPU 是 0%，而不是空转）。

**`setTimeout(fn, 0)` 和 `setImmediate(fn)` 的顺序**：

```js
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
// 主模块里：顺序不确定！取决于进程启动到这里花了多久
```

原因：`setTimeout(fn, 0)` 实际是 1ms。如果第一轮进入 timers 阶段时还没到 1ms，timer 就不执行，先跑到 check 阶段执行 immediate；如果启动慢了超过 1ms，timeout 先跑。

**但在 IO 回调里，顺序是确定的**：

```js
fs.readFile('f', () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
// 永远是 immediate 先 —— 因为当前在 poll 阶段，
// check 阶段就在后面，而 timers 要等下一轮
```

**实践含义**：需要「让出线程但尽快执行」用 `setImmediate`，它保证在当前阶段结束后的 check 阶段执行，不用等下一轮 timers。做分片处理大数组时用它，见后面「不要阻塞」那节。

# Node 20 / 22 > 运行时与事件循环 > 事件循环的六个阶段 > 微任务：Promise 和 process.nextTick 的插队

**微任务不属于六个阶段中的任何一个。它们在「每个宏任务之间」被清空。**

两个微任务队列，`nextTick` 优先级更高：

```js
console.log('1 同步');
process.nextTick(() => console.log('3 nextTick'));
Promise.resolve().then(() => console.log('4 promise'));
setTimeout(() => console.log('5 timeout'));
setImmediate(() => console.log('6 immediate'));
console.log('2 同步');

// 输出：1 同步 → 2 同步 → 3 nextTick → 4 promise → 5 timeout → 6 immediate
```

**规则**：同步代码跑完 → 清空 nextTick 队列 → 清空 microtask（Promise）队列 → 进入事件循环阶段 → **每个宏任务回调执行完，都再清空一遍两个微任务队列**。

**`await` 就是 Promise，所以也是微任务**：

```js
async function f() {
  console.log('a');
  await null;              // 这里让出，后面的代码变成微任务
  console.log('c');
}
f();
console.log('b');
// a → b → c
```

**微任务能饿死事件循环**——这是个真实的挂起场景：

```js
function loop() {
  process.nextTick(loop);    // 无限递归微任务
}
loop();
setTimeout(() => console.log('永远不会执行'), 0);
```

微任务队列在进入下一阶段前必须清空，而它永远清不完。**递归的 Promise 链也一样**。要循环让出就用 `setImmediate(loop)`——它是宏任务，会给其他阶段机会。

**什么时候用 `nextTick`**：几乎不需要。它的历史用途是「在当前操作完成后、任何 IO 之前插入逻辑」，典型是让构造函数里的 `emit` 能被外部的 `.on()` 接到：

```js
class Thing extends EventEmitter {
  constructor() {
    super();
    // this.emit('ready');              // ✗ 外部还没来得及 .on()
    process.nextTick(() => this.emit('ready'));   // ✓
  }
}
```

**新代码优先 `queueMicrotask()`**（标准 API，和浏览器一致）或者直接用 Promise。`nextTick` 是 Node 特有的，且优先级过高容易饿死循环。

# Node 20 / 22 > 运行时与事件循环 > 事件循环的六个阶段 > 不要阻塞事件循环

**只有一个线程在跑 JS。任何长时间的同步代码都让所有请求一起等。**

现象很有辨识度：**QPS 不高、CPU 接近 100%（单核）、所有接口一起变慢、P99 极高但没有一个具体的慢查询**。

**常见阻塞源**：

```js
fs.readFileSync(bigFile)           // ✗ 任何 *Sync
JSON.parse(hugeString)             // ✗ 几 MB 的 JSON 可能几百毫秒
JSON.stringify(hugeObject)         // ✗ 同理
crypto.pbkdf2Sync(...)             // ✗ 同步加密
bigArray.sort() / .map().filter()  // ✗ 百万级数组操作
new RegExp(userInput).test(s)      // ✗ 灾难性回溯（ReDoS）
while (Date.now() - t < 1000) {}   // ✗ 忙等
```

**`*Sync` 的唯一合理场景是启动阶段**（读配置、加载证书）——那时还没开始服务请求。启动后一律用异步版本。

**ReDoS 特别值得警惕**：某些正则在特定输入上是指数级复杂度。

```js
/^(a+)+$/.test('aaaaaaaaaaaaaaaaaaaaaaaaaaaX')   // 卡死几秒
```

嵌套量词（`(a+)+`、`(a*)*`）+ 不匹配的结尾是典型形态。**永远不要用用户输入构造正则**，且校验用的正则要过一遍工具（safe-regex、CodeQL）。

**CPU 密集的正确做法，三选一**：

```js
// 1. 分片让出（适合能拆的批处理）
async function processAll(items) {
  for (let i = 0; i < items.length; i++) {
    process(items[i]);
    if (i % 1000 === 0) await new Promise(r => setImmediate(r));  // 让出一轮
  }
}

// 2. worker_threads（适合单个重计算）
// 3. 丢给外部服务 / 队列（适合真的很重的任务）
```

**怎么发现阻塞**：

```bash
node --cpu-prof app.js        # 生成 .cpuprofile，Chrome DevTools 里看火焰图
```

或者线上埋一个循环延迟探针：

```js
let last = performance.now();
setInterval(() => {
  const now = performance.now();
  const lag = now - last - 500;      // 期望 500ms，多出来的就是循环延迟
  if (lag > 100) console.warn('event loop lag', lag.toFixed(0), 'ms');
  last = now;
}, 500);
```

**这个指标（event loop lag）是 Node 服务最该监控的一个**，比 CPU 使用率更能说明问题。lag 持续超过几十毫秒就说明有东西在堵。

# Node 20 / 22 > 运行时与事件循环 > 内存与垃圾回收

**V8 的堆是分代的**：

- **新生代（young generation）**——新对象放这里，很小（默认十几 MB）。用 Scavenge 算法，两个半区来回复制存活对象。绝大多数对象在这里就死了，所以很快
- **老生代（old generation）**——在新生代活过两轮的对象晋升到这里。用标记-清除 + 标记-整理，慢，会有停顿

**含义**：**短命对象几乎免费，长命对象才有代价**。所以「减少对象分配」这个优化在 Node 里通常不如「不要意外持有引用」重要。

**默认堆上限**：64 位系统上老生代约 2GB（不同版本有差异）。超了就 `FATAL ERROR: Reached heap limit - JavaScript heap out of memory`。

```bash
node --max-old-space-size=4096 app.js     # 调到 4GB
```

**容器里必须显式设置**：Node 默认按**宿主机**内存推算堆上限，容器 limit 是 512MB 而 Node 以为有 32GB，结果堆还没到上限就被 **OOMKilled**（现象是容器无预警重启，Node 日志里什么都没有）。规则是把 `--max-old-space-size` 设成容器 limit 的 **70~80%**（剩下给堆外内存：Buffer、原生模块、栈）。

**堆外内存（Buffer）不算在 max-old-space-size 里**。大量 Buffer 会让 RSS 远超堆大小。`process.memoryUsage()` 分开看：

```js
process.memoryUsage()
// { rss: 常驻总量, heapTotal: 堆申请, heapUsed: 堆使用, external: 堆外, arrayBuffers: ... }
```

**内存泄漏的四个常见形态**：

1. **模块级容器只增不减** —— `const cache = new Map()` 一直 set 不删。这是最常见的。用 `lru-cache` 设上限
2. **监听器没移除** —— `emitter.on()` 反复注册。Node 到 11 个会警告 `MaxListenersExceededWarning`，看到它先查是不是在循环/请求处理里注册的
3. **闭包意外持有大对象** —— 回调捕获了整个请求上下文或大 Buffer
4. **定时器没清** —— `setInterval` 忘了 `clearInterval`，回调里的引用永远存活

**`WeakMap` / `WeakRef`** 的键不阻止回收，做「附加数据到对象上」时用它，对象死了条目自动消失。

**排查手段**：

```bash
node --inspect app.js
# Chrome → chrome://inspect → Memory → 打两个 Heap Snapshot
# 比较（Comparison 视图），看哪类对象数量在涨、被谁引用（Retainers）
```

**方法**：压测中间打第一个快照，跑一段时间打第二个，比较增量。找 Retainers 链就能定位到具体哪个模块的哪个变量在持有。这比猜有效得多。

# Node 20 / 22 > 运行时与事件循环 > 进程：环境变量、信号与退出

**`process.env` 的值永远是字符串或 undefined**：

```js
process.env.PORT              // '3000' 字符串
Number(process.env.PORT)      // 3000
process.env.DEBUG === 'true'  // 布尔要显式比较，'false' 也是真值！
```

**配置读取要在启动时校验并 fail fast**：

```js
function requireEnv(k) {
  const v = process.env[k];
  if (!v) throw new Error(`缺少环境变量 ${k}`);
  return v;
}
const DATABASE_URL = requireEnv('DATABASE_URL');   // 启动就崩，好过运行时崩
```

**Node 20+ 原生支持 `.env`**：`node --env-file=.env app.js`，不再需要 dotenv。

**退出码**：`0` 成功，非 0 失败。`process.exit(1)` **立即退出，不等待在途的异步操作**——日志可能写不完、连接不会关。要优雅退出就走信号处理，不要直接 exit。

**优雅退出的标准形态**：

```js
const server = app.listen(3000);

async function shutdown(signal) {
  console.log(`收到 ${signal}，开始关闭`);
  server.close();                      // 停止接受新连接，在途请求继续
  await new Promise(r => server.on('close', r));
  await db.close();                    // 关数据库
  await queue.disconnect();
  process.exit(0);
}

process.on('SIGTERM', () => shutdown('SIGTERM'));   // k8s / docker stop
process.on('SIGINT', () => shutdown('SIGINT'));     // Ctrl+C
```

**为什么必须做**：k8s 滚动更新先发 SIGTERM，默认 30 秒后 SIGKILL。不处理 SIGTERM 的进程会被直接杀掉，在途请求全部 502、数据库连接泄漏。**加个超时兜底**，避免关闭流程自己卡住：

```js
setTimeout(() => process.exit(1), 10_000).unref();   // unref 让它不阻止进程退出
```

**兜底异常处理器**：

```js
process.on('uncaughtException', (err) => {
  logger.fatal(err);
  process.exit(1);                     // ✓ 记录后必须退出
});
process.on('unhandledRejection', (reason) => {
  logger.fatal(reason);
  process.exit(1);
});
```

**关键点：这两个处理器只用来记日志然后退出，不要用来「继续运行」。** 走到这里说明程序状态已经不可信（可能有半完成的事务、泄漏的锁）。Node 15+ 起 `unhandledRejection` 默认就是崩溃，这是正确的默认值。**靠进程管理器（pm2/k8s）重启，而不是靠吞异常硬撑。**

**`unref()`** 值得记：让定时器/socket 不阻止进程退出。写 CLI 工具时经常需要它——否则一个 `setInterval` 让进程永远不退出。
